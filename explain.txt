 explain.txt について（読み方ガイド）
======================================================================

このファイルは2部構成である。

  第1部「関数呼び出し構造 全一覧」（このすぐ下から始まる）
    translate_paper.py の main() を起点に、実際に呼び出される全関数
    を「本の目次」のように呼び出し順で番号付けした一覧。各関数を
    「入力」「出力」「処理内容」「テスト対象」の4項目で説明する、
    このファイルの唯一の正データ（詳細情報の集約先）。

  第2部「なぜファイル単位でこう分類されているのか」（末尾）
    第1部に登場する関数が、なぜそのスクリプトファイルに実装されて
    いるのかを、第1部の番号を参照しながら説明する。第1部の内容を
    繰り返すものではなく、同じ情報を「ファイル分割の理由」という
    別の軸で見るとどうなるか、という読み方ガイド。

（第1部の「テスト対象」欄が触れる sample0.pdf〜sample3.pdf は著作権の
都合で本リポジトリに同梱していないが、`setup_inputs.py` の実行で入手
できる。詳細はREADME.mdを参照。）

■ 全体像（呼び出し構造ベース。番号は直後の第1部と共通）

  このツールは、1本のCLIコマンド translate_paper.py の main()（1）を
  起点に、下記の呼び出し番号ツリーに沿って「ページ範囲決定 → PDF解析
  （4ステップ） → タグ解析・数式保護 → 翻訳 → PDFレンダリング」という
  一本道のパイプラインを実行する。各段階は互いの内部実装を知らず、
  データ構造（pdf_models.py / translation_models.py）だけを介して
  次の段階に渡す「バケツリレー」方式になっている。各番号の詳細
  （入力・出力・処理内容・テスト対象）はこの直後の第1部を、各行末の
  [n]が指すファイルについて「なぜそのファイルに実装されているか」は
  末尾の第2部（該当する[n]の項）を参照。

  [ユーザー]
     │ python translate_paper.py <PDF> <出力先> [--chapter/--start/--end/...]
     ▼

   ├─ 1.2  describe_page_range ………… 範囲記述子の算出 [0]
   ├─ 1.3  default_output_dir ………… 出力先自動生成（output_dir省略時のみ）[0]
   └─ 1.4  run_pipeline …………………………… パイプライン統括 [0]
        ├─ 1.4.1  process_pdf ……………… PDF解析（4ステップ） [2]
        │    ├─ 1.4.1.1 run_mineru ………… Step1: MinerU実行       [3]

        │         → page_XX_en.md / images/

             ├─ 1.4.2.1 parse_output_dir他 …… タグ付きMD読込      [9]

             ├─ 1.4.2.3 exclude_references_section ……………… [9]

                  → paper_bilingual.pdf / paper_en.pdf / paper_ja.pdf

    1.4/1.4.2/1.4.2.5/1.4.2.5.1/1.4.2.6/1.4.2.7/1.4.2.8/1.4.2.11から

■ 工程（ページ範囲決定／PDF解析／構造化・タグ処理／翻訳実行／
  翻訳後処理／PDF生成）と呼び出し番号ツリーの対応

  上記の呼び出し番号ツリーは、処理内容に着目すると6つの工程に大別
  できる。各工程は、呼び出し番号ツリー上の1つの関数、または複数の
  連なる関数の集まりに対応する。

  この区切り方は単なる分類ではなく、「外部の重い処理（MinerU・DeepL）
  を実際に再実行しないと検証できない工程」と「合成データやキャッシュ
  された実データを使えば、外部処理を一切呼ばずに単体テストできる工程」
  を分ける実務的な境界線になっている。6工程のうち実行必須なのは
  (2)と(4)の2つだけで、残り4つ（(1)(3)(5)(6)）はいずれも外部処理なしに
  独立してテストできる。

  (1) ページ範囲の決定
      対応する関数: 1.1.1〜1.1.2.3（1.1 resolve_page_rangeのサブツリー
      全体）。1.2 describe_page_range・1.3 default_output_dirも、
      resolve_page_rangeと同じCLI引数から派生する付随的な処理として
      main（1）の直下・1.4 run_pipelineより前に実行されるが、
      いずれも本編パイプラインの一部ではなく、ページ範囲そのものの
      決定には関与しない（describe_page_rangeはcache/・output/の
      フォルダ命名用の記述子を組み立てるだけ、default_output_dirは
      output_dir省略時のみ呼ばれる出力先の自動生成）。
      ▶ fitzで組み立てる合成PDFで独立テスト可能（MinerU・DeepL不要）。

  (2) PDF解析（=MinerU実行）
      対応する関数: 1.4.1.1（run_mineru）のみ。
      ▶ 6工程中、唯一の重い外部処理。cache/<PDF>_<範囲記述子>/mineru_cache/に
      永続化されており（mineru_cache.py）、これより後の工程はMinerUを
      再実行せずこのキャッシュから続きをテストできる。このキャッシュ
      が無い状態でこの工程自体を検証するには実際にMinerUを実行する
      必要がある。

  (3) 構造化・タグ処理
      対応する関数: 1.4.1.2 / 1.4.1.3 / 1.4.1.4 / 1.4.2.1 / 1.4.2.3 /
      1.4.2.4。
      一言で言うと「(2)の後処理」と「(4)の前処理」をあわせた工程。
        - (2)の後処理: 1.4.1.2 analyze_structure・1.4.1.3
          translate_units・1.4.1.4 build_documentが、MinerUの生出力
          （content_list.json）をタグ付きMarkdown（page_XX_en.md）へ
          変換する。
        - (4)の前処理: 1.4.2.1 parse_output_dir・1.4.2.3
          exclude_references_section・1.4.2.4 build_document_contextが、
          そのMarkdownを読み込んでDocUnitと文脈（document_context）を
          組み立て、(4) call_deeplがそのまま使える形に整える。
      間にタグ付きMarkdownというファイルを挟むため、番号ツリー上は
      1.4.1と1.4.2という別の親にまたがるが、間に他の工程の処理は
      挟まらず時間的には連続している。この中間表現の逆操作にあたる
      write_translated_pages（1.4.2.9）は、実行順が(5)の末尾にあたる
      ため(5)側に分類している（(5)参照）。
      ▶ 1.4.1.2以降は、MinerU由来のcontent_list形式を模した自作dict、
      または自作Markdownファイルを使えば、MinerU・DeepLどちらも
      呼ばずに独立テストできる。実DeepLを伴う実行（全体テストの実DeepL版
      test_run_pipeline_end_to_end_with_real_deepl、または人間による
      本実行）では、この工程の出力（document_context・page_XX_en.md）を
      cache/<PDF>_<範囲記述子>/real_deepl_output_<タイムスタンプ>/
      03_structured/へ保存しており、MinerU解析やタグ処理を再実行しなく
      ても内容を確認できる。ここに保存されるpage_XX_en.mdは、process_pdf
      が生成した時点の内容（(5)のprotect_confirmed_single_letter_leaks
      適用前）である点に注意（output_dir側のpage_XX_en.mdは、(5)の
      write_translated_pagesにより最終的な内容へ上書きされる）。

  (4) 翻訳実行（DeepL呼び出し・文脈構築含む）
      対応する関数: 1.4.2.5.1（call_deepl）のみ。1.4.2.5
      （run_translation）の子。
      全unitのループ・文脈（ドキュメント全体の要約＋直近3文の履歴）の
      構築・1文ずつ1.4.2.2.1 protect（数式のプレースホルダ退避、
      DeepLへの入力準備。math_protection.py内、1.4.2.2 normalizeの
      構成要素として初出済みの関数を再利用）・DeepLの実呼び出しを
      行う。DeepLからの応答テキストにはプレースホルダ（__MATHn__）が
      まだ残っており、unit.tagをキーにした辞書として、テキストと
      数式スパンの対応表（math_spans）を戻り値で返す。この時点では
      unit.ja_textは書き換えない。
      ▶ 6工程中、(2)と並んで実行必須の工程。DeepL自体の応答（言い回し
      のドリフト等）を検証したい場合はこの工程を再実行する必要がある。
      実DeepLを伴う実行（全体テストの実DeepL版
      test_run_pipeline_end_to_end_with_real_deepl、または人間による
      本実行）では、この工程への入力（unitごとのprotected_text・
      context_text）をcache/<PDF>_<範囲記述子>/real_deepl_output_
      <タイムスタンプ>/04_deepl_input/deepl_input.jsonへ、出力
      （raw_text・math_spans）をcache/<PDF>_<範囲記述子>/
      real_deepl_output_<タイムスタンプ>/04_deepl_output/
      raw_deepl_results.jsonへ、それぞれunit.tagをキーにした辞書として
      保存する。

  (5) 翻訳後処理
      対応する関数: 1.4.2.5.2（apply_restore） / 1.4.2.6〜1.4.2.9
      （check_unprotected_math_survival・
      protect_confirmed_single_letter_leaks・
      report_untranslated_fragment_candidates・write_translated_pages。
      子の1.4.2.6.1 find_unprotected_math_like_tokens・1.4.2.8.1
      find_untranslated_fragment_candidatesを含む）。
      run_translation（1.4.2.5）の子1.4.2.5.2 apply_restoreが、(4)の
      call_deepl（1.4.2.5.1）が返した辞書を受け取り、unitごとに数式
      スパンを使ってプレースホルダを元の数式へ復元し、unit.ja_textへ
      書き込む（DeepLへの再通信を伴わない決定的な処理。実体はunitごとに
      1.4.2.2.2 restoreを呼ぶ）。run_translationはcall_deepl・
      apply_restoreという2つの子を順に呼ぶだけの薄い関数であり、(4)と
      (5)の境界はこの親子関係としてコード上に現れている。
      続けてtranslate_and_export（1.4.2）自身が、1.4.2.6
      check_unprotected_math_survival（内部で1.4.2.6.1
      find_unprotected_math_like_tokensを呼ぶ）・1.4.2.7
      protect_confirmed_single_letter_leaks・1.4.2.8
      report_untranslated_fragment_candidates（内部で1.4.2.8.1
      find_untranslated_fragment_candidatesを呼ぶ）・1.4.2.9
      write_translated_pages（page_XX_ja.mdの書き出し。(3)の
      parse_output_dirの逆操作）を、この順に呼ぶ。
      ▶ 1.4.2.6〜1.4.2.9の4関数すべてが、DeepLを呼ばずオフラインで
      検証できる。
      実DeepLを伴う実行（全体テストの実DeepL版
      test_run_pipeline_end_to_end_with_real_deepl、または人間による
      本実行）では、apply_restore直後・protect_confirmed_single_
      letter_leaks適用前の状態を、cache/<PDF>_<範囲記述子>/
      real_deepl_output_<タイムスタンプ>/05_postprocess/に、役割の
      異なる2種類のファイルとして保存する（run_translation（1.4.2.5）
      が担う）。
        - units_raw.json: DocUnitリスト全体のスナップショット（JSON）。
          apply_restore以外の後処理系関数（check_unprotected_math_
          survival等）をja_text込みで検証するための入力になる。
        - page_XX_en.md / page_XX_ja.md: 同じ状態を、人間が目視確認
          しやすいタグ付きMarkdown形式で書き出したもの（write_
          translated_pagesを流用）。
      いずれも「保護前」のスナップショットである点に注意。単体アルファ
      ベット数式変数への$...$保護（1.4.2.7 protect_confirmed_single_
      letter_leaks）が適用された「保護後・最終的な」page_XX_en.md/
      page_XX_ja.mdは、cache/配下ではなくoutput_dir側にのみ存在する
      （en.mdはwrite_translated_pagesによる上書きで、ja.mdは新規書き
      出しで、それぞれoutput_dir直下に反映される）。CLAUDE.mdが定める
      許可リスト運用（未知の候補が出た場合の人間による目視確認）は、
      このoutput_dir側の最終的なpage_XX_ja.mdを対象に行う。
      apply_restore自体の検証には、04_deepl_output/raw_deepl_results.
      jsonとunits_raw.jsonを突き合わせて使う。raw_deepl_results.jsonに
      apply_restoreを通した結果を「都度その場で計算した正解データ」と
      して使うのではなく、独立に凍結されたunits_raw.jsonと比較する
      ことで、apply_restore自体にリグレッションが入っても検知できる
      （同じ関数の出力を自分自身の正解データにしてしまうと、そのリグレ
      ッションを検知できなくなるため）。

  (6) PDF生成
      対応する関数: 1.4.2.10（build_blocks） / 1.4.2.11（render_all_pdfs、
      1.4.2.11.1〜1.4.2.11.3.1.1を含む）。1.4.2の最後の2つの子。
      ▶ モック翻訳済みの自作Markdownを使えば独立テスト可能
      （test_translate_and_export_with_mocked_deeplが既に実施）。
      実DeepLを伴う実行の永続キャッシュにはPDF・画像自体は含めない。
      DeepLを呼ばず、05_postprocess/のunits_raw.jsonから決定的に
      再生成できるため、恒久的に保持する必要がないからである。

  まとめると、(1)〜(6)は6つとも、途切れず時間的に連なる1つの関数、
  またはひとまとまりの関数群に対応する。(1)(2)(4)(5)(6)は番号ツリー
  上でも隣接した位置にまとまっているが、(3)だけは「(2)の後処理」と
  「(4)の前処理」という2つの塊の組み合わせのため、番号ツリー上は
  1.4.1と1.4.2という別の親にまたがる。ただし両者の間に他の工程は
  挟まらないため、時間的な連なりとして1つであるという意味では他の
  5つと変わらない。


■ 第1部の読み方

  - 番号は呼び出し順（親の直下の子は「親番号.連番」）。番号が深い
    ほどネストした（より内側から）呼び出しであることを示す。
  - 「X.0」は例外的な表記。既に確定した番号体系の中に、実際には
    それより前に呼ばれる関数を後から挿入する必要が生じた場合に使う
    （例:「main()内で1.1（resolve_page_range）より前に呼ばれる」）。
  - 各関数のブロックは必ず「入力」「出力」「処理内容」「テスト対象」
    の4項目を持つ。引数・戻り値が複数ある場合は箇条書きでそれぞれの
    意味を記す。「テスト対象: なし」は、専用の直接テストが無く、
    上位関数のテスト実行時に間接的に実行されるのみであることを示す。
  - 同じ関数が複数箇所から呼ばれる場合、初出箇所でのみ詳細を展開し、
    以降は「→ X.X.X と同一」または「（→参照）」とだけ記す（重複説明
    を避けるため）。

 第1部: 関数呼び出し構造 全一覧（translate_paper.py の main() を起点に、
 目次形式で番号付けしたもの。同じ関数が複数箇所から呼ばれる場合は
 初出箇所でのみ展開し、以降は「→ 参照」とだけ記す。各項目は
 「入力（引数）」「出力」「処理内容」「テスト対象」の4つに分けて
 記載する）
======================================================================

1. main（translate_paper.py）
  入力: なし
  出力: なし
  処理内容: CLI引数（pdf_path, output_dir, --chapter, --start, --end,
    --start-label, --end-label）をargparseで解析し、1.0で入力PDFの
    存在を確認した上で、resolve_page_rangeでページ範囲を確定し、
    run_pipelineを呼び出す、コマンドライン実行時のエントリポイント。
  テスト対象: main自体を直接呼び出すテストは無い（CLIレベルのエンドツーエンドテストは実施していない）。

  1.0 _require_pdf_exists（translate_paper.py）
    入力:
      - pdf_path: 入力PDFファイルのパス（args.pdf_path）
    出力: なし
    処理内容: Path(pdf_path).is_file()で入力PDFファイルが実在するかを
      確認する。resolve_page_range/run_pipeline内部（fitzでのPDF読み
      込み等）は存在しないパスに対して生のFileNotFoundErrorを送出する
      が、それだと他の入力エラー（章指定・印刷ページラベルの解決失敗
      等）とは違い分かりにくいトレースバックがそのまま表示されてしま
      う。この事前チェックにより、他のエラーと同じ「分かりやすい日本
      語メッセージ＋SystemExit」の形に統一する。main()内では
      argparseの直後、resolve_page_range（1.1）より前に呼ばれる
      （番号は呼び出し順に合わせて1.0としているが、mainの子としては
      1.1と対等な最初の呼び出し先）。
    テスト対象:
      - 工程(1): test_require_pdf_exists_raises_for_missing_fileで、存在しないパスを渡した場合にfitzの生のFileNotFoundErrorではなく「入力PDFファイルが見つかりません: ...」というSystemExitになることを、test_require_pdf_exists_passes_for_existing_fileで、実在するパス（sample0.pdf）では何も送出しない（正常系）ことを確認している。

  1.1 resolve_page_range（translate_paper.py）
    入力:
      - pdf_path: 入力PDFファイルのパス
      - chapter: --chapterで指定された章番号文字列（例:"1,2"）。未指定ならNone
      - start: --startで指定された開始物理ページ番号。未指定ならNone
      - end: --endで指定された終了物理ページ番号。未指定ならNone
      - start_label: --start-labelで指定された開始印刷ページラベル。未指定ならNone
      - end_label: --end-labelで指定された終了印刷ページラベル。未指定ならNone
    出力: (開始物理ページ, 終了物理ページ)のタプル
      - 開始物理ページ: 処理対象の先頭ページ番号（1始まり）、または未指定ならNone
      - 終了物理ページ: 処理対象の末尾ページ番号（1始まり・両端含む）、または未指定ならNone
    処理内容: --start系/--start-label系の同時指定はValueErrorにし、
      「物理ページ指定 > 印刷ラベル指定 > 章指定」の優先順位でページ
      範囲を1本化する。
    テスト対象:
      - 工程(1): test_resolve_page_range_conflicting_start_and_start_label_raisesで--startと--start-labelを同時指定した場合にValueErrorになることを、test_resolve_page_range_prefers_page_label_over_chapterで--start-label/--end-labelが--chapterより優先して解決されることを確認している。

    1.1.1 resolve_physical_page_range（pdf_page_label_resolver.py）

            1.4.1.2.1.2.0 wrap_bare_greek_letters（pdf_text_utils.py。
                restore_merged_hyphens（1.4.1.2.1.2.1）より前に呼ばれる
                ため、番号体系を崩さず挿入する「X.0」表記に倣う）

              出力: ギリシャ文字をTeXコマンド形式で$...$に包んだ後の文字列
                （数式スパン部分は元のまま）
              処理内容: $...$の数式部分を避けつつ（restore_merged_hyphensと
                同じ_INLINE_MATH_REによるスキップ方式）、本文中に単独で
                現れるギリシャ文字（α-ω, Α-Ω）を検出し、_GREEK_TO_TEX_
                COMMAND（vendor/katex/katex.min.jsの記号定義から抽出した
                対応表。例:"γ"→"gamma"）でTeXコマンド形式に変換した上で
                $...$に包む（例:"scale γ"→"scale $\gamma$"）。地の文に
                ギリシャ文字が実在の英単語として使われることは無いため、
                半角英数字1文字（"x"や"K"等）とは異なり自動保護しても
                誤爆リスクが低いと判断できる。MinerUが数式として検出
                しなかった"scale γ"（sample0.pdf page_02、P2-FIG1-
                CAPTION-S3）のような漏れを、翻訳前の構造解析段階で
                プレースホルダ保護できるようにする（math_protection.py
                のprotect/restoreは翻訳直前に呼ばれるため、この時点で
                $...$に入っていれば自動的に保護対象になる）。

                なぜ生の文字ではなくTeXコマンド形式に変換するか:
                vendor/katex/katex.min.js（KaTeX 0.16.11）を調査した
                ところ、"se(...,"γ","\\gamma",...)"のように、
                KaTeXは生のUnicodeギリシャ文字を対応するTeXコマンドの
                エイリアスとして内部登録しており、描画結果は生の文字
                でも\gammaコマンドでも等価になることを確認している
                （つまり動作上はどちらでも問題ない）。それでも、MinerU
                由来の他の数式スパンが全てTeXコマンド形式であることと
                の表記の一貫性のため、明示的にコマンド形式へ変換する。
                ラテン文字と同形の一部の大文字ギリシャ文字（Α,Β,Ε,Ζ,
                Η,Ι,Κ,Μ,Ν,Ο,Ρ,Τ,Χ）はKaTeXに専用コマンドが無いため、
                _GREEK_TO_TEX_COMMANDに含めず、変換せず元の文字のまま
                $...$で囲む仕様とした。

            対し、_UNPROTECTED_MATH_RE（`\b[a-zA-Z]\s*=\s*[a-zA-Z0-9]+\b`）
            で数式らしき未保護の断片をヒューリスティックに検出する。
            MinerUの数式検出は完全ではなく、同じ表現でも文によって
            $...$で囲まれないことがあるため（例: page_02_en.mdの
            "t = 1 to t = 0"はEQ検出から漏れている）、その見逃しを
            機械的に洗い出す目的。単独の変数名（"z"や"K"等、"="を伴わない
            もの）は英単語との区別が付かないため意図的に対象外。
          テスト対象:
            - 工程(5): test_find_unprotected_math_like_tokensで、"t = 1"/"t = 0"の
              検出、$...$保護済みスパンの除外、"="を伴わない単独文字が
              検出されないことを直接検証している。

      1.4.2.7 protect_confirmed_single_letter_leaks（math_protection.py）
        入力:

          - log: 情報メッセージを受け取るコールバック（既定はprint）
        出力: 情報メッセージのリスト（無ければ空リスト）
        処理内容: 翻訳対象unitごとに1.4.2.8.1 find_untranslated_
          fragment_candidatesで候補を検出し、そのうち半角アルファベット
          1文字だけの候補（例:"x","K"）に限定して、en_text・ja_text

          残らないため、翻訳後も半角のまま生き残っている単体アルファ
          ベットは数式変数である可能性が高いと判断できる（"DiT"や

          後から$...$を挿入するだけの後処理）。置換の際はunit.en_text/
          unit.ja_textをそれぞれ1.4.2.2.1 protect / 1.4.2.2.2 restoreで

          保護済みの数式スパン（例:"$p ( y \mid x )$"）の内部にある
          同名の文字は二重に囲まれない。
        処理内容の呼び出し元: translate_and_export（1.4.2）が、
          1.4.2.6 check_unprotected_math_survival直後・
          1.4.2.8 report_untranslated_fragment_candidatesより前に
          本番実行のたびに自動的に呼び出す。
        テスト対象:
          - 工程(5): test_protect_confirmed_single_letter_leaks_wraps_matching_
            occurrencesで、未保護の単体アルファベット（"z"）が

            existing_math_spansで、既に$...$保護済みのスパン内部にある

            壊さないことを、test_protect_confirmed_single_letter_leaks_
            skips_multi_char_tokensで、"DiT"のような複数文字のトークン

        1.4.2.8.1 find_untranslated_fragment_candidates（math_protection.py）
          入力:
            - ja_text: 検査対象の日本語訳文字列
          出力: 未検出（未保護）の数式らしき候補断片のリスト
          処理内容: 日本語訳では地の文がほぼ全て全角文字になる一方、
            DeepLが自然言語として翻訳しない固有名詞・数式的表記は半角の
            まま残る傾向があることを利用する。protectで保護済み数式
            スパンを除いたja_textから、非空白の半角文字（またはギリシャ
            文字α-ω/Α-Ω）で始まり終わる区間（スペースを挟んだ"t = 1"
            のような表記も1区間としてまとめる）を抽出し、(a)英字または
            ギリシャ文字を1つ以上含む、(b)4文字以下または"()=_^{}"等の
            記号を含む、の両方を満たすものを候補として返す。
            find_unprotected_math_like_tokens（1.4.2.6.1）より広い網だが、
            "FLUX"や"DiT"のような短い固有名詞・"(i)(ii)(iii)"のような
            列挙記号も誤検知として拾う（人間が確認する前提のヒューリス
            ティック）。

            既知の限界（裸の数字1文字だけの数式漏れ）: 上記(a)の条件
            （英字/ギリシャ文字を1つ以上含む）により、"$...$"で保護
            されていない裸の数字1つだけの数式漏れ（例: page_02の
            "from t = 1 to 0 with K discrete steps"の"0"。"t = 1"側は
            $...$には保護されていないが"="を含むため検出されるのに対し、
            "0"は単独の数字のため検出されない）は検出できない。この
            条件を外すと、見出し番号("1."）・節番号の参照("2.2"）・
            引用番号("[12]"）等、本文中に大量に存在する正当な半角の裸
            数字を誤検知してしまい実用にならないため、意図的な設計上の
            トレードオフとして残している。この種の裸数字の漏れは、
            KNOWN_LEAKED_MATH_FRAGMENTS（上記1.4.2.8参照）に人間が
            目視確認した結果として記録する運用でカバーする。
          テスト対象:
            - 工程(5): test_find_untranslated_fragment_candidatesで、
              "t = 1"/"t = 0"のようなスペースを含む断片が分断されず1つに

     │      └─> pdf_document_builder.py ─> PIL(画像保存)
     │      （上記すべてが pdf_models.py の型でデータをやり取り）
     ├─> md_tag_parser.py ─> translation_models.py
     ├─> deepl_translator.py
     │      ├─> math_protection.py
     │      └─> deepl(外部ライブラリ) ─> DeepL API(外部サービス)
     └─> pdf_renderer.py
            ├─> katex_assets.py ─> vendor/katex/(同梱アセット)
            └─> playwright(外部ライブラリ) ─> Chromium(外部プロセス)

  ※ pdf_text_utils.py と pdf_models.py / translation_models.py は
    他のどのパイプラインモジュールにも依存しない「末端」モジュール
    （依存されるだけで、何も呼び出さない）。


■ なぜこの構成になっているか（設計意図のまとめ）

  1. 「解析（MinerU起点）」と「翻訳・PDF生成（DeepL/Playwright起点）」を
     完全に分離し、間を「タグ付きMarkdown」というテキスト形式の
     成果物で受け渡す設計になっている。これにより、
       - 一度Markdownまで生成すれば、DeepL APIキーの問題やPDF
         レンダリングの調整だけを translate_and_export() で
         やり直せる（MinerUの重い解析を再実行せずに済む）。
       - 各層をpytestで個別にテストしやすい。
  2. PDF解析自体も4ステップ（MinerU実行／構造解析／翻訳／結合）に
     分解されており、それぞれが pdf_models.py の型のみに依存する
     ことで、将来的にMinerU以外の解析エンジンや別の翻訳エンジンに
     差し替える場合も、影響範囲を該当ステップ内に閉じ込められる
     ようになっている。
  3. 数式（math_protection.py, katex_assets.py）や参考文献
     （md_tag_parser.py の exclude_references_section）など、
     「翻訳してはいけない／翻訳が壊れやすい」要素の保護ロジックを
     専用モジュールとして切り出し、本流のパイプラインコードを
     汚さないようにしている。
