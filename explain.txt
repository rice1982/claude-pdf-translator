 explain.txt について（読み方ガイド）
======================================================================

このファイルは2部構成である。

  第1部「関数呼び出し構造 全一覧」（このすぐ下から始まる）
    translate_paper.py の main() を起点に、実際に呼び出される全関数
    を「本の目次」のように呼び出し順で番号付けした一覧。各関数を
    「入力」「出力」「処理内容」「テスト対象」の4項目で説明する、
    このファイルの唯一の正データ（詳細情報の集約先）。

  第2部「なぜファイル単位でこう分類されているのか」（末尾）
    第1部に登場する関数が、なぜそのスクリプトファイルに実装されて
    いるのかを、第1部の番号を参照しながら説明する。第1部の内容を
    繰り返すものではなく、同じ情報を「ファイル分割の理由」という
    別の軸で見るとどうなるか、という読み方ガイド。

（第1部の「テスト対象」欄が触れる sample0.pdf〜sample3.pdf は著作権の
都合で本リポジトリに同梱していないが、`setup_inputs.py` の実行で入手
できる。詳細はREADME.mdを参照。）

■ 全体像（呼び出し構造ベース。番号は直後の第1部と共通）

  このツールは、1本のCLIコマンド translate_paper.py の main()（1）を
  起点に、下記の呼び出し番号ツリーに沿って「ページ範囲決定 → PDF解析
  （4ステップ） → タグ解析・数式保護 → 翻訳 → PDFレンダリング」という
  一本道のパイプラインを実行する。各段階は互いの内部実装を知らず、
  データ構造（pdf_models.py / translation_models.py）だけを介して
  次の段階に渡す「バケツリレー」方式になっている。各番号の詳細
  （入力・出力・処理内容・テスト対象）はこの直後の第1部を、各行末の
  [n]が指すファイルについて「なぜそのファイルに実装されているか」は
  末尾の第2部（該当する[n]の項）を参照。

  [ユーザー]
     │ python translate_paper.py <PDF> <出力先> [--chapter/--start/--end/...]
     ▼
  1.   main ……………………………………………… エントリポイント [0]
   ├─ 1.0  _require_pdf_exists …………… 入力PDF存在確認 [0]
   ├─ 1.1  resolve_page_range …………… ページ範囲の決定 [0]
   │    ├─ 1.1.1 resolve_physical_page_range（印刷ラベル→物理ページ）[1]
   │    └─ 1.1.2 resolve_chapter_page_range（章番号→物理ページ）    [1]
   └─ 1.2  run_pipeline …………………………… パイプライン統括 [0]
        ├─ 1.2.1  process_pdf ……………… PDF解析（4ステップ） [2]
        │    ├─ 1.2.1.1 run_mineru ………… Step1: MinerU実行       [3]
        │    ├─ 1.2.1.2 analyze_structure  Step2: 構造解析         [4]
        │    │     （文字列処理の実体は pdf_text_utils.py）        [5]
        │    ├─ 1.2.1.3 translate_units … Step3: 翻訳（現状素通し）[6]
        │    └─ 1.2.1.4 build_document … Step4: 成果物結合         [7]
        │         → page_XX_en.md / images/
        └─ 1.2.2  translate_and_export … タグ解析・翻訳・PDF生成 [0]
             ├─ 1.2.2.1 parse_output_dir他 …… タグ付きMD読込      [9]
             ├─ 1.2.2.2 normalize（数式保護）………………………………… [10]
             ├─ 1.2.2.3 exclude_references_section ……………… [9]
             ├─ 1.2.2.4 build_document_context …………………… [9]
             ├─ 1.2.2.5 run_translation [0]
             │     └─ 1.2.2.5.1 translate_with_deepl（実DeepL通信）[11]
             └─ 1.2.2.6/.7 build_blocks／render_all_pdfs ……… [12]
                  → paper_bilingual.pdf / paper_en.pdf / paper_ja.pdf

  （1.3 _log は上記どの枝にも属さない横断的なユーティリティで、
    1.2/1.2.2/1.2.2.5/1.2.2.5.1/1.2.2.7から進捗ログ出力のために
    呼ばれる。translate_paper.py [0] に実装。）


■ 工程（ページ範囲決定／PDF解析／構造化・タグ処理／翻訳実行／
  翻訳後処理／PDF生成）と呼び出し番号ツリーの対応

  上記の呼び出し番号ツリーは、処理内容に着目すると6つの工程に大別
  できる。各工程が呼び出し番号ツリーの「どこからどこまで」にあたるかを
  示す。

  この区切り方は単なる分類ではなく、「外部の重い処理（MinerU・DeepL）
  を実際に再実行しないと検証できない工程」と「合成データやキャッシュ
  された実データを使えば、外部処理を一切呼ばずに単体テストできる工程」
  を分ける実務的な境界線になっている。6工程のうち実行必須なのは
  (2)と(4)の2つだけで、残り4つ（(1)(3)(5)(6)）はいずれも外部処理なしに
  独立してテストできる。1.2.2（translate_and_export）の子は、後述の
  通りこの工程の順序（3→4→5→6）のまま呼び出される。

  (1) ページ範囲の決定
      = 1.1 resolve_page_range のサブツリー全体（1.1.1〜1.1.2.3）。
      main（1）の直下、1.2 run_pipelineより前に実行される前処理で、
      1.2以降の本編パイプラインには含まれない。
      ▶ fitzで組み立てる合成PDFで独立テスト可能（MinerU・DeepL不要）。

  (2) PDF解析（=MinerU実行）
      = 1.2.1.1 run_mineruのみ。
      ▶ 6工程中、唯一の重い外部処理。cache/<PDF>/mineru_cache/に
      永続化されており（mineru_cache.py）、これより後の工程はMinerUを
      再実行せずこのキャッシュから続きをテストできる。このキャッシュ
      が無い状態でこの工程自体を検証するには実際にMinerUを実行する
      必要がある。

  (3) 構造化・タグ処理
      = 1.2.1.2（analyze_structure、構造解析）・1.2.1.3
      （translate_units、現状素通し）・1.2.1.4（build_document、
      成果物結合）・1.2.2.1（parse_output_dir系。1.2.2.1.1〜1.2.2.1.3
      を含む）・1.2.2.2（exclude_references_section）・1.2.2.3
      （build_document_context）。
      1.2.1側（構造解析〜成果物結合）はタグ付きMarkdown
      （page_XX_en.md）を書き出す側、1.2.2側（parse_output_dir系・
      参考文献除外・文脈構築）はそれを読み込みDocUnitへ戻す側であり、
      両者は「タグ付きMarkdownという共通の中間表現」を挟んだ対の関係に
      あるため、1つの工程としてまとめている。
      ▶ 1.2.1.2以降は、MinerU由来のcontent_list形式を模した自作dict、
      または自作Markdownファイルを使えば、MinerU・DeepLどちらも
      呼ばずに独立テストできる。実DeepLテストでは、この工程の出力
      （document_context・page_XX_en.md）を
      cache/<PDF>/real_deepl_output/03_structured/へ保存しており、
      MinerU解析やタグ処理を再実行しなくても内容を確認できる。

  (4) 翻訳実行（DeepL呼び出し・文脈構築含む）
      = 1.2.2.4（run_translation）の子である1.2.2.4.1 call_deepl。
      全unitのループ・文脈（ドキュメント全体の要約＋直近3文の履歴）の
      構築・1文ずつ1.2.2.4.1.1 protect（数式のプレースホルダ退避、
      DeepLへの入力準備）・DeepLの実呼び出しを行う。DeepLからの応答
      テキストにはプレースホルダ（__MATHn__）がまだ残っており、
      unit.tagをキーにした辞書として、テキストと数式スパンの対応表
      （math_spans）を戻り値で返す。この時点ではunit.ja_textは
      書き換えない。
      ▶ 6工程中、(2)と並んで実行必須の工程。DeepL自体の応答（言い回し
      のドリフト等）を検証したい場合はこの工程を再実行する必要がある。
      実DeepLテストでは、この工程への入力（unitごとのprotected_text・
      context_text）をcache/<PDF>/real_deepl_output/04_deepl_input/
      deepl_input.jsonへ、出力（raw_text・math_spans）を
      cache/<PDF>/real_deepl_output/04_deepl_output/
      raw_deepl_results.jsonへ、それぞれunit.tagをキーにした辞書として
      保存する。

  (5) 翻訳後処理
      = 1.2.2.4（run_translation）のもう一方の子である1.2.2.4.2
      apply_restore（(4)が返した辞書を受け取り、unitごとに数式スパンを
      使ってプレースホルダを元の数式へ復元し、unit.ja_textへ書き込む。
      DeepLへの再通信を伴わない決定的な処理で、実体はunitごとに
      1.2.2.4.2.1 math_protection.restoreを呼ぶ）と、1.2.2.5
      check_unprotected_math_survival（内部で1.2.2.5.1
      find_unprotected_math_like_tokensを呼ぶ）・1.2.2.6
      protect_confirmed_single_letter_leaks・1.2.2.7
      report_untranslated_fragment_candidates（内部で1.2.2.7.1
      find_untranslated_fragment_candidatesを呼ぶ）。run_translation
      （1.2.2.4）はcall_deepl（(4)）とapply_restore（(5)の先頭）という
      2つの子を順に呼ぶだけの薄い関数であり、(4)と(5)の境界はこの
      親子関係としてコード上に現れている。
      ▶ 4関数すべてが、DeepLを呼ばずオフラインで検証できる。
      実DeepLテストでは、この工程の出力を
      cache/<PDF>/real_deepl_output/05_postprocess/に、役割の異なる
      2種類のファイルとして保存する。
        - units_raw.json: (4)(5)実行後・protect_confirmed_single_
          letter_leaks適用前のDocUnitリスト全体のスナップショット。
          apply_restore以外の後処理系関数（check_unprotected_math_
          survival等）をja_text込みで検証するための入力になる。
        - page_XX_ja.md: protect_confirmed_single_letter_leaks適用後の
          最終的な翻訳済みMarkdown。CLAUDE.mdが定める許可リスト運用
          （未知の候補が出た場合の人間による目視確認）のために保存する。
      apply_restore自体の検証には、04_deepl_output/raw_deepl_results.
      jsonとunits_raw.jsonを突き合わせて使う。raw_deepl_results.jsonに
      apply_restoreを通した結果を「都度その場で計算した正解データ」と
      して使うのではなく、独立に凍結されたunits_raw.jsonと比較する
      ことで、apply_restore自体にリグレッションが入っても検知できる
      （同じ関数の出力を自分自身の正解データにしてしまうと、そのリグレ
      ッションを検知できなくなるため）。
      なお1.2.2.8 write_translated_pages（page_XX_ja.mdの書き出し）は
      (5)の直後・(6)の直前に呼ばれるが、(1)が1.2の外側に置かれている
      のと同様、6工程のいずれにも属さない独立したステップとして扱う。

  (6) PDF生成
      = 1.2.2.9（build_blocks）・1.2.2.10（render_all_pdfs、配下の
      1.2.2.10.1〜1.2.2.10.3.1.1をすべて含む）。1.2.2の最後の2つの子。
      ▶ モック翻訳済みの自作Markdownを使えば独立テスト可能（スイートG
      が既に実施）。実DeepLテストの永続キャッシュにはPDF・画像自体は
      含めない。DeepLを呼ばず、05_postprocess/のunits_raw.jsonから
      決定的に再生成できるため、恒久的に保持する必要がないからである。

  まとめると、(1)〜(6)はいずれも呼び出しツリー上で1つの枝（または、
  親1つとその直下の子だけで完結する枝）がそのまま1つの工程に対応
  する。1.2.2（translate_and_export）の子（1.2.2.1〜1.2.2.10）も、
  1.2.2.4の内部（call_deepl→apply_restore）も、いずれも工程の順序
  （3→4→5→［どの工程にも属さないwrite_translated_pages］→6）と
  一致する並びで呼ばれており、番号順がそのまま呼び出し順・工程順を
  表す。これはmd_tag_parser.py（タグ解析）とmath_protection.py
  （数式保護）が異なるファイルに分離されていること自体の設計判断とは
  別の話で、「1.2.2という1つの関数が、複数の責務を持つヘルパーを
  どの順に呼ぶか」という実行順の整理である（なぜ2ファイルに分けたか
  の設計理由は第2部[9][10]を参照）。


■ 第1部の読み方

  - 番号は呼び出し順（親の直下の子は「親番号.連番」）。番号が深い
    ほどネストした（より内側から）呼び出しであることを示す。
  - 「X.0」は例外的な表記。既に確定した番号体系の中に、実際には
    それより前に呼ばれる関数を後から挿入する必要が生じた場合に使う
    （例:「main()内で1.1（resolve_page_range）より前に呼ばれる」）。
  - ただし兄弟番号同士の順序は、常に実行時の時系列と一致するとは
    限らない。特に1.2.2 translate_and_exportの子（1.2.2.1〜1.2.2.7）
    は目次上の整理を優先した番号付けになっており、実際の呼び出し順は
    1.2.2の「処理内容」に個別に記載している（例:1.2.2.2.4/1.2.2.2.6/
    1.2.2.2.7は1.2.2.5の完了後に呼ばれる。詳細は上記「工程」の対応
    表(3)(4)を参照）。
  - 各関数のブロックは必ず「入力」「出力」「処理内容」「テスト対象」
    の4項目を持つ。引数・戻り値が複数ある場合は箇条書きでそれぞれの
    意味を記す。「テスト対象: なし」は、専用の直接テストが無く、
    上位関数のテスト実行時に間接的に実行されるのみであることを示す。
  - 同じ関数が複数箇所から呼ばれる場合、初出箇所でのみ詳細を展開し、
    以降は「→ X.X.X と同一」または「（→参照）」とだけ記す（重複説明
    を避けるため）。


======================================================================
 第1部: 関数呼び出し構造 全一覧（translate_paper.py の main() を起点に、
 目次形式で番号付けしたもの。同じ関数が複数箇所から呼ばれる場合は
 初出箇所でのみ展開し、以降は「→ 参照」とだけ記す。各項目は
 「入力（引数）」「出力」「処理内容」「テスト対象」の4つに分けて
 記載する）
======================================================================

1. main（translate_paper.py）
  入力: なし
  出力: なし
  処理内容: CLI引数（pdf_path, output_dir, --chapter, --start, --end,
    --start-label, --end-label）をargparseで解析し、1.0で入力PDFの
    存在を確認した上で、resolve_page_rangeでページ範囲を確定し、
    run_pipelineを呼び出す、コマンドライン実行時のエントリポイント。
  テスト対象: main自体を直接呼び出すテストは無い（CLIレベルのエンドツーエンドテストは実施していない）。

  1.0 _require_pdf_exists（translate_paper.py）
    入力:
      - pdf_path: 入力PDFファイルのパス（args.pdf_path）
    出力: なし
    処理内容: Path(pdf_path).is_file()で入力PDFファイルが実在するかを
      確認する。resolve_page_range/run_pipeline内部（fitzでのPDF読み
      込み等）は存在しないパスに対して生のFileNotFoundErrorを送出する
      が、それだと他の入力エラー（章指定・印刷ページラベルの解決失敗
      等）とは違い分かりにくいトレースバックがそのまま表示されてしま
      う。この事前チェックにより、他のエラーと同じ「分かりやすい日本
      語メッセージ＋SystemExit」の形に統一する。main()内では
      argparseの直後、resolve_page_range（1.1）より前に呼ばれる
      （番号は呼び出し順に合わせて1.0としているが、mainの子としては
      1.1と対等な最初の呼び出し先）。
    テスト対象:
      - スイートJ（入力PDFファイル存在チェック）: test_require_pdf_exists_raises_for_missing_fileで、存在しないパスを渡した場合にfitzの生のFileNotFoundErrorではなく「入力PDFファイルが見つかりません: ...」というSystemExitになることを、test_require_pdf_exists_passes_for_existing_fileで、実在するパス（sample0.pdf）では何も送出しない（正常系）ことを確認している。

  1.1 resolve_page_range（translate_paper.py）
    入力:
      - pdf_path: 入力PDFファイルのパス
      - chapter: --chapterで指定された章番号文字列（例:"1,2"）。未指定ならNone
      - start: --startで指定された開始物理ページ番号。未指定ならNone
      - end: --endで指定された終了物理ページ番号。未指定ならNone
      - start_label: --start-labelで指定された開始印刷ページラベル。未指定ならNone
      - end_label: --end-labelで指定された終了印刷ページラベル。未指定ならNone
    出力: (開始物理ページ, 終了物理ページ)のタプル
      - 開始物理ページ: 処理対象の先頭ページ番号（1始まり）、または未指定ならNone
      - 終了物理ページ: 処理対象の末尾ページ番号（1始まり・両端含む）、または未指定ならNone
    処理内容: --start系/--start-label系の同時指定はValueErrorにし、
      「物理ページ指定 > 印刷ラベル指定 > 章指定」の優先順位でページ
      範囲を1本化する。
    テスト対象:
      - スイートI（ページ範囲決定ロジックの優先順位）: test_resolve_page_range_conflicting_start_and_start_label_raisesで--startと--start-labelを同時指定した場合にValueErrorになることを、test_resolve_page_range_prefers_page_label_over_chapterで--start-label/--end-labelが--chapterより優先して解決されることを確認している。

    1.1.1 resolve_physical_page_range（pdf_page_label_resolver.py）
      入力:
        - pdf_path: 入力PDFファイルのパス
        - start_label: 開始印刷ページラベル（例:"cov","i","36"）。Noneなら変換しない
        - end_label: 終了印刷ページラベル。Noneなら変換しない
      出力: (開始物理ページ, 終了物理ページ)のタプル
        - 開始物理ページ: start_labelに対応する物理ページ番号（int）。start_labelがNoneならNone
        - 終了物理ページ: end_labelに対応する物理ページ番号（int）。end_labelがNoneならNone
      処理内容: start_label/end_labelそれぞれについて1.1.1.1を呼び出し、
        印刷ページラベルを物理ページ番号へ変換する。
      テスト対象:
        - スイートH（印刷ページラベル解決）: test_resolve_physical_page_range_matches_previously_verified_pagesで、印刷ページ番号にギャップ（欠番）がある場合でも開始・終了ラベルから物理ページ範囲へ正しく変換されることを、合成PDF（ラベル"4"を欠番にしたもの）で確認している。

      1.1.1.1 resolve_physical_page（pdf_page_label_resolver.py）
        入力:
          - pdf_path: 入力PDFファイルのパス
          - label: 変換したい印刷ページラベル1つ（例:"cov","i","xviii","36"）
        出力: 対応する物理ページ番号（int、1始まり）
        処理内容: fitzでPDFを開き全ページのget_label()を走査し、大文字
          小文字を無視して一致するページを探す（見つからなければ
          PageLabelResolutionError）。
        テスト対象:
          - スイートH（印刷ページラベル解決）: test_resolve_physical_page_for_sample3で"cov"/"COV"/"Cover"/"i"/"xviii"/"55"/"60"等のラベルが正しい物理ページ番号に変換されることを、test_resolve_physical_page_unknown_label_raisesで存在しないラベルを指定した場合にPageLabelResolutionErrorになることを、test_resolve_physical_page_without_page_labels_raisesで印刷ページラベル情報を持たないPDFではエラーになることを確認している。

    1.1.2 resolve_chapter_page_range（pdf_chapter_resolver.py）
      入力:
        - pdf_path: 入力PDFファイルのパス
        - chapter_spec: 章指定文字列（例:"1,2"や"1-2"）

                restore_merged_hyphens（1.2.1.2.1.2.1）より前に呼ばれる

              処理内容: $...$の数式部分を避けつつ（restore_merged_hyphensと
                同じ_INLINE_MATH_REによるスキップ方式）、本文中に単独で
                現れるギリシャ文字（α-ω, Α-Ω）を検出し、_GREEK_TO_TEX_
                COMMAND（vendor/katex/katex.min.jsの記号定義から抽出した
                対応表。例:"γ"→"gamma"）でTeXコマンド形式に変換した上で
                $...$に包む（例:"scale γ"→"scale $\gamma$"）。地の文に
                ギリシャ文字が実在の英単語として使われることは無いため、
                半角英数字1文字（"x"や"K"等）とは異なり自動保護しても
                誤爆リスクが低いと判断できる。MinerUが数式として検出

                $...$に入っていれば自動的に保護対象になる）。

                vendor/katex/katex.min.js（KaTeX 0.16.11）を調査した

                （つまり動作上はどちらでも問題ない）。それでも、MinerU
                由来の他の数式スパンが全てTeXコマンド形式であることと
                の表記の一貫性のため、明示的にコマンド形式へ変換する。

      1.2.2.2.5 find_untranslated_fragment_candidates（math_protection.py）
        入力:
          - ja_text: 検査対象の日本語訳文字列
        出力: 未検出（未保護）の数式らしき候補断片のリスト
        処理内容: 日本語訳では地の文がほぼ全て全角文字になる一方、
          DeepLが自然言語として翻訳しない固有名詞・数式的表記は半角の
          まま残る傾向があることを利用する。protectで保護済み数式
          スパンを除いたja_textから、非空白の半角文字（またはギリシャ
          文字α-ω/Α-Ω）で始まり終わる区間（スペースを挟んだ"t = 1"
          のような表記も1区間としてまとめる）を抽出し、(a)英字または
          ギリシャ文字を1つ以上含む、(b)4文字以下または"()=_^{}"等の
          記号を含む、の両方を満たすものを候補として返す。
          find_unprotected_math_like_tokens（1.2.2.2.3）より広い網だが、
          "FLUX"や"DiT"のような短い固有名詞・"(i)(ii)(iii)"のような
          列挙記号も誤検知として拾う（人間が確認する前提のヒューリス
          ティック）。

          既知の限界（裸の数字1文字だけの数式漏れ）: 上記(a)の条件
          （英字/ギリシャ文字を1つ以上含む）により、"$...$"で保護
          されていない裸の数字1つだけの数式漏れ（例: page_02の
          "from t = 1 to 0 with K discrete steps"の"0"。"t = 1"側は
          $...$には保護されていないが"="を含むため検出されるのに対し、
          "0"は単独の数字のため検出されない）は検出できない。この
          条件を外すと、見出し番号("1."）・節番号の参照("2.2"）・
          引用番号("[12]"）等、本文中に大量に存在する正当な半角の裸
          数字を誤検知してしまい実用にならないため、意図的な設計上の
          トレードオフとして残している。この種の裸数字の漏れは、
          スイートKのKNOWN_LEAKED_MATH_FRAGMENTS（下記1.2.2.2.6参照）
          に人間が目視確認した結果として記録する運用でカバーする。
        テスト対象:
          - スイートC（文字列処理ユーティリティ単体テスト）:
            test_find_untranslated_fragment_candidatesで、"t = 1"/
            "t = 0"のようなスペースを含む断片が分断されず1つにまとまる
            ことに加え、ギリシャ文字("γ")が半角英数字と同様に候補として
            検出されることを含め、6ケースを直接検証している。
          - スイートK（DeepL実課金統合テスト）: 実際のDeepL翻訳結果
            （page_01_ja.md/page_02_ja.md）に対して実行し、検出された
            候補が人間確認済みの許可リストの範囲内にあることを確認
            している（許可リストの詳細はtestExplain.txtスイートK参照）。
            裸の数字1つだけの数式漏れ"0"（上記「既知の限界」参照）は
            本関数では検出されないが、目視確認によりKNOWN_LEAKED_
            MATH_FRAGMENTS（下記参照）へ別途記録している。

      1.2.2.2.7 protect_confirmed_single_letter_leaks（math_protection.py）
        入力:
          - units: DocUnitのリスト（翻訳済み、en_text/ja_text設定済みのもの）
          - log: 情報メッセージを受け取るコールバック（既定はprint）
        出力: 情報メッセージのリスト（無ければ空リスト）
        処理内容: 翻訳対象unitごとに1.2.2.2.5 find_untranslated_
          fragment_candidatesで候補を検出し、そのうち半角アルファベット
          1文字だけの候補（例:"x","K"）に限定して、en_text・ja_text
          双方の該当箇所に直接$...$を挿入し保護する。実在の英単語
          （"I"や"a"等）は通常の翻訳で全角の日本語に置き換わり候補として
          残らないため、翻訳後も半角のまま生き残っている単体アルファ
          ベットは数式変数である可能性が高いと判断できる（"DiT"や
          "NMS"のような複数文字のトークンは実在の固有名詞・略語と
          区別できないため対象外のまま、1.2.2.2.6のログのみで扱う）。
          DeepLへの再翻訳は行わない（1回目の翻訳で確定済みのテキストに
          後から$...$を挿入するだけの後処理）。置換の際はunit.en_text/
          unit.ja_textをそれぞれ1.2.2.2.1 protect / 1.2.2.2.2 restoreで
          一時的にプレースホルダへ退避してから行うため、既に$...$で
          保護済みの数式スパン（例:"$p ( y \mid x )$"）の内部にある
          同名の文字は二重に囲まれない。
        処理内容の呼び出し元: translate_and_export（1.2.2）が、
          1.2.2.2.4 check_unprotected_math_survival直後・
          1.2.2.1.3 write_translated_pagesより前に本番実行のたびに
          自動的に呼び出す。
        テスト対象:
          - スイートC（文字列処理ユーティリティ単体テスト）:
            test_protect_confirmed_single_letter_leaks_wraps_matching_
            occurrencesで、未保護の単体アルファベット（"z"）が
            en_text/ja_text双方の同じ箇所で$...$に置き換わることを、
            test_protect_confirmed_single_letter_leaks_does_not_touch_
            existing_math_spansで、既に$...$保護済みのスパン内部にある
            同名の文字（"$p ( y \mid x )$"内の"x"）を二重に囲んで
            壊さないことを、test_protect_confirmed_single_letter_leaks_
            skips_multi_char_tokensで、"DiT"のような複数文字のトークン
            は対象外のままであることを、test_protect_confirmed_single_
            letter_leaks_skips_non_translatable_unitsで、翻訳対象外
            unitは無視されることを直接検証している。
          - スイートK（DeepL実課金統合テスト）:
            test_page_ja_md_and_candidate_detection_against_real_deepl
            が、本番のtranslate_and_exportと同じ位置で本関数を実際の
            DeepL翻訳結果に対して実行し、"x"/"y"/"z"/"K"が以降の全数
            チェックで候補として検出されなくなる（＝保護された）ことを
            間接的に確認している。

          実装上の注意点: 置換をen_text/ja_textへ直接（protect/restore
          を経由せず）適用する実装は避けること。既に$...$で保護済みの
          数式スパンの内部にある同名の文字まで誤って二重に$で囲んで
          しまい、数式スパンが破損する（例:"$p ( y \mid x )$"が
          "$p ( $y$ \mid $x$ )$"のように壊れる）。上記の通りprotect/
          restoreを経由する実装にすることで、既存スパンの内部を
          変更しないようにしている。

      1.2.2.3 exclude_references_section（md_tag_parser.py）
        入力:

■ なぜこの構成になっているか（設計意図のまとめ）

  1. 「解析（MinerU起点）」と「翻訳・PDF生成（DeepL/Playwright起点）」を
     完全に分離し、間を「タグ付きMarkdown」というテキスト形式の
     成果物で受け渡す設計になっている。これにより、
       - 一度Markdownまで生成すれば、DeepL APIキーの問題やPDF
         レンダリングの調整だけを translate_and_export() で
         やり直せる（MinerUの重い解析を再実行せずに済む）。
       - 各層をpytestで個別にテストしやすい。
  2. PDF解析自体も4ステップ（MinerU実行／構造解析／翻訳／結合）に
     分解されており、それぞれが pdf_models.py の型のみに依存する
     ことで、将来的にMinerU以外の解析エンジンや別の翻訳エンジンに
     差し替える場合も、影響範囲を該当ステップ内に閉じ込められる
     ようになっている。
  3. 数式（math_protection.py, katex_assets.py）や参考文献
     （md_tag_parser.py の exclude_references_section）など、
     「翻訳してはいけない／翻訳が壊れやすい」要素の保護ロジックを
     専用モジュールとして切り出し、本流のパイプラインコードを
     汚さないようにしている。
