# PDF学術論文・書籍 構造化・翻訳ツール

英語の学術論文・書籍のPDFを解析してタグ付き構造化Markdownを生成し、
さらに日本語訳と3種類のPDF（対訳版／英語版／日本語版）を出力するツールです。
本文・図表・数式を座標情報から分離抽出し、1文ごとにユニークID（例:
`[P1-S1]`）を付与することで、原文と訳文を文単位で正確に対応付けます。

※ 本ツールは現在Windows環境（コマンドプロンプト／PowerShell）での動作を
  前提としています。macOS/Linuxでの動作確認は行っていません。

※ 本リポジトリをClaude Code等のAIコーディングエージェントで操作する場合、
  `--dangerously-skip-permissions`（ファイル編集・コマンド実行の許可確認を
  省略する起動オプション）の使用にはリスクが伴います。使用する場合は
  仮想環境（VM）等の隔離された環境下での運用を、リスクを避けたい場合は
  当該オプションを付けない通常モード（`claude`コマンド、都度確認あり）
  の利用を推奨します。

## 主な機能

このソフトウェアは、英語の学術論文や書籍のPDFを入力として、以下の処理を
1つのコマンドで実行します。

1. **PDF解析（MinerUによるレイアウト解析）**
   本文・図表・数式・メタ情報（タイトル／著者／所属）を分離抽出し、
   1文ごとにユニークID（例: `[P1-S2-abstract-S2]`）を付与した
   ページ別Markdownを生成します。
   図・表・数式領域はPNG画像として切り出します。
   ヘッダー（実行見出し・arXiv ID等）、フッター、ページ番号などの
   不要テキストは、MinerUが要素ごとに付与する種別に基づいて除外します。

2. **日本語訳**
   翻訳にはDeepL API（要APIキー・実際に課金される）を使用します
   （[設定・環境変数](#設定環境変数)参照）。各文の翻訳リクエストに、
   文書全体の要約と直前2〜3文の原文を`context`パラメータとして渡し、
   代名詞や専門用語の表記揺れを抑えます。文単位で逐次送信します。
   APIキー未設定・文字数上限到達・通信エラーなどが発生した場合は、
   エラーとして処理を終了します。
   翻訳結果は、最終PDFとは別に`page_XX_ja.md`（`page_XX_en.md`と同じ
   タグ形式）としても出力されます。PDFをレンダリングせずテキストの
   まま原文と見比べられるので、翻訳内容を目視確認したい場合に使えます。

   MinerUの数式検出は完全ではなく、英字を含まない裸の数字（例: "を0
   まで積分する"の"0"）や、"DiT"のような英大文字の略称・固有名詞
   （実在の略語なのか変数名なのか機械的に区別できないもの）のような
   数式らしき文字列・記号が`$...$`で保護されないまま地の文に残ることが
   あります（数式保護の仕組み自体は`mainCode/stage6/stage6.py`参照）。
   本ツールは翻訳後の`page_XX_ja.md`に半角のまま残った断片をヒューリス
   ティックに洗い出し（`find_untranslated_fragment_candidates`）、その
   うち半角アルファベット1文字だけの変数を自動的に`$...$`で保護します
   （`protect_confirmed_single_letter_leaks`）。「英字1文字 = 値」形式
   （例: "t = 1"）や裸のギリシャ文字は、翻訳前の工程(2)であらかじめ
   保護されます（`wrap_bare_letter_equals_expressions` /
   `wrap_bare_greek_letters`）。自動保護の対象にならなかった候補
   （固有名詞・型番等の誤検知を含みうるヒューリスティックのため）は、
   ご自身で`page_XX_ja.md`と原本PDFを見比べて判断してください。処理は
   止まりません。

   さらに、"P($A$, $B$)"のように、関数呼び出し記法の引数部分だけが
   個別に`$...$`保護され、識別子や括弧自体が地の文として残るケースに
   ついては、識別子（英字1〜4文字）に**空白なしで**続く`(`から対応する
   `)`までの中に保護済みスパンが含まれる場合に限り、自動的に
   `"$P(A, B)$"`のように1つの数式へまとめ直します
   （`merge_function_call_math_spans`）。カンマ区切りの列挙に加え、
   条件付き確率の"|"区切り表記（例:"P(A | B)"）や、プライム記号を含む
   更新後の値の表記（例:"P(X'|Y)"。DeepLの翻訳結果ではUnicodeの
   右シングルクォーテーションマーク"'"が使われることがあり、両方に
   対応）も対象です。安全性を優先し、識別子と`(`の間に空白がある場合
   （固有名詞＋丸括弧書き、例:"BSDS500 (K=10)"、との誤認を避けるため）
   や、アンダースコア区切りの複合識別子（例:"D_KL(...)"）、引数部に
   保護済みスパンが1つも無い場合は対象外とします。

   詳細は `doc\architecture\stage6.md`・`doc\architecture\stage2.md`
   （工程(2)）を参照して
   ください。`testCode/test_integration.py`の
   `test_untranslated_fragment_candidates_against_cached_deepl_output`
   では、実際のDeepL翻訳結果に対して
   `find_untranslated_fragment_candidates`で検出される候補が、人間確認済みの
   許可リスト（誤検知／本物の数式漏れ）の範囲内に収まっているかを
   継続的に検証しています。

3. **ページ指定・章指定処理**
   長大なPDFや書籍向けに、処理対象の「物理ページ範囲（--start, --end）」、
   「印刷ページラベル範囲（--start-label, --end-label）」、または
   「章（--chapter）」を指定して、必要な箇所のみを高速かつ安全に処理できます。

4. **PDF生成**
   以下3種類のPDFを自動生成します。
   - 対訳版PDF（左：英語 / 右：日本語、文単位で行を揃えて対応）
   - 英語版のみPDF
   - 日本語版のみPDF

   文中のインライン数式（例: p(y|x)）はKaTeXにより実際の数式として
   描画されます（生のLaTeXテキストのままにはなりません）。
   参考文献（References）セクションは、著者名等の誤翻訳を防ぐため
   翻訳対象から除外され、原文のまま出力されます。

### 既知の限界（サマリー）

詳細な説明は以下の各項目を参照してください。

| 項目 | 現状の挙動 | 理由 |
| --- | --- | --- |
| 表の下の脚注 | 表キャプションの続き文として結合されて出力される（内容は失われない） | キャプションと脚注を意味的に区別する専用タグが無いため |
| ピリオド区切りのキャプション（例: "Table 1. ..."） | 2文（CAPTION-S1/S2）に分かれて出力されることがある | 文分割ロジックの略語リスト仕様の都合 |
| 番号なし見出し（例: "ABSTRACT"） | 見出し専用タグにならず本文の1文として出力される | 意図的な仕様（後続文は暗黙的に同じセクション名でグルーピングされ、章区切りの機能は保たれる） |
| 物理ページをまたぐ段落 | MinerUが1つのitemと認識した場合、段落全体が開始側ページのMarkdownに出力される | MinerUのページ判定をそのまま尊重し、item単位の再分割は行わないため |
| インライン数式の判定 | 変数のイタリック体・太字等を手がかりに人が最終確認する必要がある | PDFの見た目だけでは元のLaTeXが数式モードだったか完全には証明できないため |
| 未保護の数式らしき断片（固有名詞・略語、裸の数字1つ等） | 単体アルファベット1文字は自動`$...$`保護される。それ以外は自動保護されず、無課金の回帰テストと人間の目視確認で扱う | 固有名詞・略語との機械的な区別ができず、見出し番号・節番号参照・引用番号との誤検知を避けるため意図的に対象外としている箇所がある |
| 関数呼び出し記法の引数だけが個別に保護される場合（例:"P(A,B)"の"A"・"B"のみ） | 識別子直後に空白なしで`(`が続く場合のみ自動的に1つの数式へまとめ直す。空白がある場合や"D_KL("のような複合識別子は対象外 | 固有名詞＋丸括弧書きとの誤認を避けるための安全策（詳細は`mainCode/stage6/stage6.py`のdocstring参照） |
| 既存の`$...$`スパン直後に比較演算子付きの断片が続く場合（例:"$K$ > 1"） | 右辺が数値または別の`$...$`スパンの場合のみ自動的に1つの数式へまとめ直す（`merge_comparison_math_spans`） | 自然文（"$X$ > many models"）との誤認を避けるための安全策 |
| 上記2つのまとめ直し処理は、翻訳後の日本語文でのみパターン検出を行う | 検出された文字列が英語原文に一字一句一致する場合のみ、英語原文側にも同じ修正を反映する | 翻訳されない英語原文は全体が半角文字のため、日本語文と同じ検出ロジックを独立に適用すると誤爆しうる（詳細は`mainCode/stage6/stage6.py`のdocstring参照） |
| MinerUバックエンド`pipeline`が、数式でない単体の英字（例: 文頭の不定冠詞"A"/"a"）を数式変数と誤認し`$...$`保護してしまう場合がある | 誤って保護済み扱いになるため、本ツールの検出・自動保護のいずれの対象にもならない | `pipeline`バックエンドの数式検出精度の限界（詳細はCLAUDE.md参照） |
| 数式のPDF描画結果 | 自動テストなし | 出力PDFを開いての人間による目視確認が必要 |

以下、各項目の詳細です。

※ 表の下に印字される脚注（例:"*Our own implementation..."）は、
  内容が失われることはありませんが、表キャプションの続き文として
  結合され出力されます（キャプションと脚注を意味的に区別する
  タグは無い）。詳細は`testExplain.txt`の「工程(3)」を参照してください。

※ "Table 1. Correspondences..."のようにピリオドで区切られた
  キャプションは、文分割ロジックの略語リストの都合上、"Table 1."と
  それ以降の説明文が別々の2文（CAPTION-S1/S2）に分かれて出力される
  ことがあります。内容は失われず生成PDF上も問題ありません。

※ "ABSTRACT"のような番号の付かない見出しは、"1. INTRODUCTION"の
  ような番号付き見出し（`[P1-HEADING-...]`）とは異なり、見出し用の
  専用タグにはならず本文の1文（例: `[P1-S1-abstract-S1] ABSTRACT`）
  として出力されます。後続の文は暗黙的に同じセクション名
  （"abstract"）でグルーピングされるため、章の区切りとしての機能は
  保たれます。意図的な仕様です。

※ 段落が原本PDFの物理ページをまたいでいる場合、MinerUがその段落を
  1つのまとまり（text item）として認識していると、段落全体が
  開始側ページのMarkdownに出力されます（例: 物理2ページ目に印字
  された文が`page_01_en.md`に含まれる）。本ツールはMinerUのページ
  判定をそのまま尊重しており、item単位の再分割は行わないため、
  意図的に許容している既知の挙動です。

※ 文中のインライン数式が本当に数式として扱われるべきかは、原本PDF
  上で変数がイタリック体・ベクトル/行列が太字（`\mathbf`等）になって
  いるかを手がかりに人間が判断できますが、元のLaTeXソースが本当に
  数式モードだったかをPDFの見た目だけから完全に証明することは
  できません（単純な1文字の変数などは判断材料が乏しくなります）。
  詳細は`testExplain.txt`の「工程(3)」を参照してください。

※ 既知の限界: "$...$"で保護されず、かつ英字/ギリシャ文字を伴わない
  裸の数字1つだけの数式漏れ（例: "...to 0 with K discrete steps"の
  "0"）は、見出し番号・節番号参照・引用番号との誤検知を避けるため
  意図的に`find_untranslated_fragment_candidates`の検出対象外としており、
  自動保護もされません。

※ 既知の限界: 関数呼び出し記法のまとめ直し（`merge_function_call_math_spans`）は、
  識別子が英字のみ・1〜4文字の場合にしか対応していません。入れ子の
  関数呼び出し（例:"f(g($x$))"）や、ハイフン区切りの複合識別子
  （例:"sub-loss("）は対象外です。

※ この数式描画結果（PDFに実際に正しく描画されているか）を検証する
  自動テストは存在せず、`testExplain.txt`の「工程(7)」に記載の通り、
  出力PDFを開いての人間による目視確認が必要です。


## 前提条件・動作環境

- **OS**: Windows（コマンドプロンプト／PowerShell）。macOS/Linuxでの動作確認は行っていません。
- **Python**: 3.13以上
- **主要ライブラリ**: `requirements.txt`に、PDF解析用（pymupdf, mineru 等）と
  翻訳・PDF生成用（python-dotenv, deepl, playwright）の両方が含まれています。
- **PDF生成エンジン**: Playwright経由のChromium（[インストール手順](#インストール手順)参照）。
- **翻訳エンジン**: DeepL API。実行にはDeepL APIキーが必須です
  （[設定・環境変数](#設定環境変数)参照。無料プランのキーでも利用可能ですが、
  文字数消費に応じて課金されます）。
- 数式描画用のKaTeXは `vendor\katex` フォルダにフォント込みで同梱済みのため、
  追加のダウンロードは不要です（KaTeX本体はMITライセンスで配布されており、
  ライセンス全文は`vendor\katex\LICENSE`を参照してください）。


## インストール手順

### 1. Python仮想環境と必要ライブラリ

以下を実行して、プロジェクトフォルダ直下に venv（仮想環境）を構築してください。

```
python -m venv venv
venv\Scripts\pip install -r requirements.txt
```

### 2. Playwright（PDF生成エンジン）のブラウザ本体の導入

PDF生成にはPlaywright経由のChromiumを使用します。ライブラリ本体を
pipで入れただけではブラウザの実体が無いため、初回のみ以下を実行して
Chromiumをダウンロードしてください（数百MB程度）。

```
venv\Scripts\python -m playwright install chromium
```

インストール後、[設定・環境変数](#設定環境変数)に進んでDeepL APIキーを
設定してください（翻訳の実行に必須です）。


## 使い方

### 基本の実行方法

まずプロジェクトフォルダ直下で仮想環境を有効化します（コマンドプロンプトの場合）。

```
venv\Scripts\activate
```

PowerShellの場合は以下を使用してください。

```
venv\Scripts\Activate.ps1
```

有効化すると、プロンプトの先頭に `(venv)` が表示されます。以降は以下の形式で実行します。

```
python translate_paper.py <PDFファイルのパス> [出力先ディレクトリ] [オプション]
```

`<出力先ディレクトリ>` が既存の場合は中身が上書き再生成されます。
存在しない場合は自動的に作成されます。省略した場合は
`output\manual_{PDF名}_{範囲記述子}_{実行日時}`という名前で
自動生成されます（`--chapter`/`--start`・`--end`/`--start-label`・
`--end-label`の指定内容から範囲記述子が決まります。
例: 範囲指定なしなら`full`、`--start-label 55
--end-label 60`なら`label55-60`）。

※ 仮想環境を有効化せずに実行したい場合は、`venv\Scripts\python.exe` を直接指定しても同様に動作します（本マニュアルの他のコマンド例も同じ考え方で読み替え可能です）。

### 利用可能なオプション（CLI引数）

- `--chapter <章番号>`
  処理対象の章を指定します（例: `--chapter 1`）。
  PDFの目次（TOC/Outline）から該当する章の物理ページ範囲を自動解析して処理します。

- `--start <開始物理ページ番号>`
  処理を開始するPDFの物理ページ番号（1始まりの絶対インデックス）を指定します。

- `--end <終了物理ページ番号>`
  処理を終了するPDFの物理ページ番号（1始まりの絶対インデックス）を指定します。

- `--start-label <開始印刷ページラベル>`
  本に印刷されている見た目上のページ表記（例: "cov", "i", "xviii", "36" 等）で
  開始ページを指定します。

- `--end-label <終了印刷ページラベル>`
  本に印刷されている見た目上のページ表記（例: "41" 等）で終了ページを指定します。

※ `--start-label` / `--end-label` または `--start` / `--end` が明示的に指定された場合は、
  `--chapter` よりも優先されます。

- `--mineru-backend <pipeline|vlm-engine>`
  使用するMinerUバックエンドを指定します。既定は`pipeline`（軽量・高速）。
  `vlm-engine`はCPUのみの環境でも動作しますが大幅に低速な代わりに、
  数式・OCRの認識精度が高くなります。

### 実行具体例

※ 本リポジトリには著作権の都合上テスト用サンプルPDFを同梱していません。
  以下の`sample0.pdf`・`sample3.pdf`はファイル名の例です。お手元の
  PDF（自身が著作権を保有する、または再配布・処理が許諾されているもの）
  を`input\`フォルダに配置し、ファイル名を読み替えて実行してください。

- 論文サンプル（2ページ）を実行:
  ```
  venv\Scripts\python translate_paper.py input\sample0.pdf output\sample0
  ```

- 書籍（sample3.pdf）の第1章のみを処理:
  ```
  venv\Scripts\python translate_paper.py input\sample3.pdf output\sample3_ch1 --chapter 1
  ```

- 書籍（sample3.pdf）の物理ページ 67〜72 を指定して処理:
  ```
  venv\Scripts\python translate_paper.py input\sample3.pdf output\sample3_p67_72 --start 67 --end 72
  ```

- 書籍（sample3.pdf）の印刷ページラベル "55"〜"60" を指定して処理（物理67〜72に相当）:
  ```
  venv\Scripts\python translate_paper.py input\sample3.pdf output\sample3_label55_60 --start-label 55 --end-label 60
  ```

- 論文サンプル（2ページ）を、認識精度の高いvlm-engineバックエンドで実行:
  ```
  venv\Scripts\python translate_paper.py input\sample0.pdf output\sample0_vlm --mineru-backend vlm-engine
  ```

### 実行結果

指定した出力先ディレクトリの直下に、以下のファイルが生成されます。

```
page_01_en.md, page_02_en.md, ...   … ページ別タグ付きMarkdown（原文）
page_01_ja.md, page_02_ja.md, ...   … ページ別タグ付きMarkdown（訳文）
images/                              … 抽出された図・表・数式のPNG画像
paper_bilingual.pdf                  … 対訳版PDF
paper_en.pdf                         … 英語版のみPDF
paper_ja.pdf                         … 日本語版のみPDF
```

### 処理時間の目安

PDF解析（MinerU）はCPU実行のため、1PDFあたり数分〜十数分程度
かかることがあります（範囲指定・章指定を行うことで大幅に短縮可能です）。
翻訳・PDF生成はページ数・文数に応じて数十秒〜数分程度です。
処理中はターミナルに進捗状況（「[DeepL] P1-S5 を翻訳中...」等）が
表示されます。


## 設定・環境変数

翻訳にはDeepL APIを使用するため、DeepL APIキーの設定が必須です。

### DeepL APIキーの設定（必須）

1. DeepLアカウント（無料プランで可）を作成し、APIキーを発行します。
   https://www.deepl.com/ja/pro-api

2. プロジェクトフォルダ直下に `.env` という名前のファイルを作成し、
   以下の1行を記述します（実際のキーに置き換えてください）。

   ```
   DEEPL_API_KEY="発行されたAPIキー:fx"
   ```

   ※ 無料プランのキーは末尾が `:fx` になります。
   ※ `.env` は .gitignore で除外済みのため、Gitには含まれません。

   APIキーが未設定の場合、翻訳処理はエラーとして終了します。無料プランでも
   文字数消費に応じて課金対象になるため、長大なPDFは章・ページ範囲を絞って
   処理することを推奨します。


## テストデータの準備とテスト実行

### テストデータの準備方法

`pytest`実行や動作確認には、`input/sample0.pdf`〜`sample3.pdf`という
サンプルPDFが必要です。著作権の都合上これらのPDFファイル自体は
リポジトリに含めていないため、以下のセットアップスクリプトを実行して
`input/`フォルダに準備してください。

```
venv\Scripts\python setup_inputs.py
```

実行すると以下が行われます。

- `input/`フォルダを作成します（無い場合）。
- `sample1.pdf`をarXiv.orgの公式URL
  （https://arxiv.org/pdf/2602.16238v1 ）から都度ダウンロードします。
- ダウンロードした`sample1.pdf`の最初の2ページを抽出し、軽量テスト用の
  `sample0.pdf`として保存します。
- `sample2.pdf`をarXiv.orgの公式URL
  （https://arxiv.org/pdf/2409.00102v1 ）から都度ダウンロードします。
  バージョンを`v1`に明示固定しており、著者が将来この論文を改訂しても
  取得内容（ページ構成・キャプション文言等）が変わらないようにして
  います（`testCode/`配下のsample2.pdf依存テストはこの内容を
  前提にハードコードされているため）。
- `sample3.pdf`をSpringer（オープンアクセス書籍）の公式URL
  （https://link.springer.com/content/pdf/10.1007/978-981-95-1327-7.pdf ）
  から都度ダウンロードします。
- `sample0.pdf`〜`sample3.pdf`それぞれの著作権表示
  （`sample0_NOTICE.txt`〜`sample3_NOTICE.txt`）を`input/`直下に
  書き出します。

いずれも既にファイルが存在する場合は再ダウンロードせずスキップします。
`input/`配下のファイルは`.gitignore`で除外済みのため、Gitには含まれません。

※ **sample2.pdfのライセンスについての注意**: `sample2.pdf`は
  arXiv版（著者投稿稿）をダウンロードします。この論文の査読済み・出版版
  （Royal Society Open Science誌、DOI: 10.1098/rsos.241678）は
  CC BY 4.0で公開されていますが、出版社側のPDF配信はボット対策により
  スクリプトから自動取得できないため、内容が同一のarXiv版
  （arXiv.orgの非独占配布ライセンス）を代わりに取得しています。
  詳細は`sample2_NOTICE.txt`を参照してください。

※ **sample3.pdfのダウンロードについての注意**: SpringerのPDF配信は
  ボット対策（Client Challenge）を備えており、PythonのurllibからGETすると
  弾かれてPDFの代わりにJavaScriptチャレンジページが返ってくることを
  確認しています。そのためスクリプト内部ではWindows標準同梱の`curl`
  コマンドをサブプロセスとして呼び出してダウンロードしています。
  この方法は将来的にSpringer側の対策強化やcurlの有無によって失敗する
  可能性があります。自動ダウンロードに失敗した場合（エラーメッセージが
  表示される、または生成されたファイルがPDFとして開けない場合）は、
  お手数ですがブラウザで上記URLに直接アクセスしてPDFをダウンロードし、
  `input\sample3.pdf`として手動配置してください。

**テストデータの利用方針**:
本リポジトリは、テスト目的で学術論文を動的に取得するスクリプトを
含んでいます。これらのスクリプトは個人の非営利的な研究およびローカル
環境での検証のみを目的としています。各論文の改変や解析結果の利用に
ついては、それぞれの著者のライセンスおよび適用される著作権法を遵守し、
ユーザー自身の責任において行ってください。

### MinerU実行結果のローカルキャッシュについて

MinerUによるPDF解析結果（`content_list.json`相当のデータおよび抽出画像）は、
`cache/<PDFファイル名>_<範囲記述子>/mineru_cache/`に自動的にキャッシュ
されます（範囲記述子は`--chapter`/`--start`・`--end`/`--start-label`・
`--end-label`の指定内容から決まります。例:"full"、"label55-60"）。
`--mineru-backend`に既定の`pipeline`以外（`vlm-engine`）を指定した場合は
`mineru_cache_<backend>/`（例:"mineru_cache_vlm-engine"）という別サブ
フォルダに保存され、`pipeline`実行時のキャッシュとは独立して管理されます。
このキャッシュは`pytest`実行と、`translate_paper.py`による
手動実行のどちらからも共有されます（対象PDFファイルの内容・ページ範囲・
MinerUのバージョンが一致する限り再利用されます）。

- 初回実行時は通常通りMinerUが起動するため時間がかかりますが、2回目以降、
  同一PDF・同一ページ範囲・同一MinerUバージョンでの実行はキャッシュから
  即座に結果が返るため大幅に高速化されます。
- MinerUをアップグレードした場合や、`input/`配下のPDFファイルを別内容の
  ものに差し替えた場合は、自動的にキャッシュが無効化され再実行されます。
  手動でのキャッシュ削除は不要です。
- 明示的にキャッシュを無視して常に実行させたい場合は、環境変数
  `MINERU_CACHE_DISABLE=1`を設定してください。
- `cache/`は`input/`・`output/`と同様、著作権上の理由から`.gitignore`で
  除外されておりGit管理対象外です。ディスク容量が気になる場合は
  `cache/`ごと削除しても問題ありません（次回実行時に自動再生成されます）。
- 翻訳を実行するたびに、DeepLとの実際の送受信内容が同じ
  `cache/<PDFファイル名>_<範囲記述子>/`配下の`real_deepl_output_<実行日時>/`
  （`mineru_cache/`のきょうだいフォルダ）にも記録されます。単体
  アルファベット数式変数への`$...$`保護、および
  関数呼び出し記法の引数だけが個別に保護された断片の統合（いずれも
  [主な機能]参照）が適用される直前の状態の`page_XX_en.md`/`page_XX_ja.md`も
  人間が読める形式で含まれるため、翻訳内容を後から見直したい場合や、
  未保護の数式らしき候補を確認したい場合に利用できます（保護適用後の
  最終版は、通常通り出力先ディレクトリの同名ファイルで確認できます）。
  こちらは実行のたびにタイムスタンプ付きの新しいフォルダに書き込まれる
  ため、過去の実行結果を上書きすることはありません。

### テスト（pytest）の実行について

`testCode/`配下のテストの一部は、`input/sample0.pdf`〜
`sample3.pdf`という特定のサンプルPDFを前提に書かれています（詳細は
`testExplain.txt`の各項目の「該当関数」欄を参照）。前述の通り、
著作権の都合上これらのサンプルPDFは本リポジトリに含まれていないため、
**`input/`フォルダにこれらのファイルを配置しない限り、該当するテストは
実行できません**。対象PDFが存在しない場合の挙動はテストによって異なり、
`processed`系のfixtureを使うテストや、個別に存在チェックを持つテストは
`pytest.skip`で穏やかにスキップされますが、存在チェックを持たない一部の
テスト（`resolve_physical_page`や`resolve_chapter_page_range`を実PDFに
対して直接呼ぶもの等）はPDFが無いとエラーで失敗します。詳細はtestExplain.txt
冒頭の注記を参照してください。

なお、`resolve_chapter_page_range`・`resolve_physical_page`が実装する
「章番号→ページ範囲」「印刷ページラベル→物理ページ番号」の変換ロジック
自体は、特定の論文・書籍の内容には依存しない汎用的なアルゴリズムです。
そのためテストの大部分は、ダウンロードした実PDFではなく、テスト実行時に
`fitz`（PyMuPDF）で組み立てる目次・印刷ページラベルのみを持つ使い捨ての
合成PDFを使って検証しており、これらは`input/`フォルダにサンプルPDFが
無くても実行できます。実際の学術論文・書籍PDFに対する統合的な確認（目次や
印刷ページラベルを`fitz`が正しく読み取れているか）は、各アルゴリズムに
つき1テストだけ意図的に実データ（`sample2.pdf`/`sample3.pdf`）のまま残して
います。`testCode/`配下のテスト全体のうち、実際にダウンロードしたPDFの
中身に依存しているのは一部のみで、残りは合成データまたはPDFを使わない
純粋なロジックテストです（内訳はtestExplain.txt参照）。

pytestをそのまま実行できるようにしたい場合は、前述の「テストデータの
準備方法」の`setup_inputs.py`を実行するか、`sample0.pdf`〜`sample3.pdf`
という名前で、ご自身が著作権を保有する、または再配布・処理が許諾されて
いるPDFを`input/`フォルダに配置してください。
（`sample0.pdf`は2ページ程度の論文抜粋、`sample1.pdf`/`sample2.pdf`は
表を含む論文フルサイズ、`sample3.pdf`は目次・印刷ページラベルを持つ
大型書籍、という形式のPDFを想定して書かれたテストです。異なる形式の
PDFを使う場合、一部のテスト（実データの文言をハードコードしているもの）
は失敗する可能性があります。）

## トラブルシューティング

**Q. 書籍全体を処理しようとすると時間がかかりすぎる／DeepLの文字数が切れる。**
A. `--chapter 1` や `--start-label` / `--end-label` オプションを使用して、必要な章や印刷ページ範囲に絞って処理を実行してください。DeepL APIの文字数上限・課金にも注意してください。

**Q. 「DEEPL_API_KEY が未設定です」というエラーで処理が終了する。**
A. プロジェクトフォルダ直下に `.env` ファイルが無いか、`DEEPL_API_KEY` が正しく記述されていません。[設定・環境変数](#設定環境変数)の手順に従ってAPIキーを設定してください。

**Q. PDFの日本語が文字化けする／表示されない（豆腐文字）。**
A. 通常はWindows標準の游ゴシック/メイリオ等にフォールバックするため発生しませんが、発生する場合はPlaywrightのChromiumが正しくインストールされているか（[インストール手順](#インストール手順)）を確認してください。

**Q. 前書き（ローマ数字ページ）がある書籍で、見た目のページ番号と出力ファイル番号がずれる。**
A. `--start` / `--end` はPDF全体の絶対物理ページ数を指定する仕様です。本に印刷されている見た目通りの数字（例: 表紙 "cov"、前書き "i", "ii"、本文 "36" 等）で範囲指定したい場合は、`--start-label 55 --end-label 60` を使用してください。
